# 二期、三期和未来扩展路线

## 二期：离线局域网模式

目标是在没有互联网和中心服务器的局域网中，让节点之间直接建立连接，数据不经过固定主机中继。所有节点继续运行同一套核心，新增局域网传输适配器和发现机制。可以使用 mDNS/DNS-SD（例如 Rust 的 `mdns-sd`）发布和发现节点，也保留手动输入 IP 作为故障排查路径。

2026-10-26 讨论已确认局域网模式继续使用 FRP；建议按需在目标设备运行 frps，具体部署需验证。当前方向为暂缓局域网单跳中继，首版按仅两端直连推进。已确认内容与待验证方案见 [离线局域网与单跳讨论](lan-mode-and-single-hop-relay.md)。

局域网模式至少需要重新定义群组名称、配对码或群组密钥、节点名称、发现范围、信任模型和双向控制权限。发现服务可以帮助找到节点，但不应成为数据转发中心；会话数据最终直接在两个节点之间传输。二期开始前需要单独评审是否允许互相控制、是否支持无密码临时群组以及如何处理多个群组共用一个局域网。

## 三期：虚拟机间控制模式

目标是宿主机和多个虚拟机之间在虚拟机网卡被破坏时仍能通信。新增 `VmChannel` 适配器，优先使用 hypervisor 提供的 vsock、VMCI 或同类宿主机通道。宿主机代理负责通道创建和权限校验，虚拟机内的 StarBridge 核心继续使用统一的节点、会话和能力模型。

当前建议先支持一台宿主机控制多台虚拟机；未来的虚拟机间通信可由固定宿主机协调或中转，不以 LAN 单跳实现为前提。这些通道仍依赖对应虚拟设备驱动、内核或集成支持，不能承诺在缺少全部相关驱动时可用。拓扑、平台差异、FRP 适配边界，以及普通／局域网／虚拟机模式和模式说明的 UI 预留要求，见 [虚拟机通道与多模式规划](vm-channel-and-mode-planning.md)。本轮只记录需求，不设计或实现 UI。

三期开始前需要确认支持的 hypervisor、Windows/Linux 客户端组合、vsock CID 或 VMCI 地址分配、快照恢复后的身份持久性以及宿主机对虚拟机的授权边界。不能把虚拟机通道直接当作二期局域网的一个端口参数。

## UI 外壳替换

一期先使用本地浏览器。核心服务保持版本化的本地 API 和 WebSocket 事件协议，未来可以接入 Electron、Tauri 或 Flutter 外壳。UI 不应直接读取 FRP 配置或管理子进程，所有操作通过核心 API 完成。

## 电源和远程控制能力

未来的开机、关机、重启、桌面控制等能力应以能力插件或 `CapabilityProvider` 建模，例如 `PowerCapability`、`RemoteControlCapability`。每个能力都要有显式权限、审计记录、目标节点确认和可撤销令牌。需要管理员权限的动作通过独立的受限 helper 执行，不让主进程长期以管理员身份运行。

## 统一抽象

节点只描述身份、能力和可达性；会话描述发起端、目标端、策略和状态；传输适配器描述 Internet FRP、LAN Direct、VM Channel 等具体路径。二期和三期都必须复用这些抽象，并在实现前重新进行威胁建模和运维评审。
