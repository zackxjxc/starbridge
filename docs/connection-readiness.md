# 连接通道就绪确认

此前发起端发现目标已发布 SSH 主机公钥，就启动本地 FRP visitor 并验证 SSH。接收端按三秒心跳获取新会话，且先发布公钥、后启动接收代理，因此公钥存在不代表本次会话的代理已经注册。首次 XTCP 检查可能返回目标不存在，并触发 FRP v0.71.1 至少十秒的轮次间隔。

现在发起端先确认当前会话对应的接收代理在线，再启动 visitor 和首次 SSH 验证。直连转中转时也重新确认 STCP 代理，旧 XTCP 就绪结果不能放行新路径。就绪后重新读取目标主机公钥，避免把上一会话缓存的密钥写入新 SSH 配置；最终成功仍以固定主机身份及随机回显验证为准。

中心沿用 `GET /api/v1/sessions/{id}`，增加可选查询 `ready_path=direct|relay`。查询时通过受保护的 FRPS 管理接口检查当前代理名称与在线状态，并在请求前后复核账号、设备凭据、会话存活及路径。管理请求期间不持应用状态锁，管理响应和凭据不会发给客户端。

响应保持原会话 JSON，额外提供可选 `receiver_ready`：`true` 表示对应代理在线，`false` 表示继续等待。旧中心忽略查询参数，或中心未配置受管 FRPS 时省略该字段，客户端保留原建连流程。缺失／已结束会话、参与者或路径不匹配，以及管理接口失败均不能当作就绪。

客户端每次查询最长两秒，总等待预算十五秒，轮询间隔二百五十毫秒。等待期间及响应后均检查连接代次、账号代次和取消状态；迟到的成功响应不能恢复已终止连接。同账号并发刷新访问令牌时，可以使用已轮换的新令牌重试。

本次优化消除目标代理尚未注册造成的额外重试，不改变直连失败转中转的策略，也不保证 STUN、网络协商或 SSH 验证的固定耗时。旧接收端可配合新版中心和发起端工作；旧中心下保持兼容行为，提速需要中心支持就绪查询。

验证包括 101 项 Rust 测试、10 项打包测试，以及使用官方 FRP／OpenSSH 的隔离客户端实际建连。实测区分首次连接与重连、直连与中转，并记录 STUN 超时及首轮目标不存在次数。

## 本机隔离实测（2026-10-26）

使用相同的官方 FRP／OpenSSH、本地受管中心与两个独立客户端档案，自动连接模式下先后各测一轮冷连接和三轮热重连；各轮均进行真实 SSH 随机回显验证并确认断开后再开始下一轮。

| 项目 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 首次冷连接 | 8.210 秒 | 8.223 秒 |
| 三次重连 | 12.829／12.794／12.825 秒 | 5.643／5.902／5.662 秒 |
| 重连中位数 | 12.825 秒 | 5.662 秒 |
| 首轮目标不存在次数 | 3 | 0 |
| 最终直连成功 | 4／4 | 4／4 |

本轮重连中位数减少 7.163 秒，约 56%；冷连接基本不变。该结果属于同一 Windows 主机上隔离实例的对照实验，不代表所有网络的固定时延。其他诊断样本仍观察到默认 STUN 服务响应超时；这种网络探测失败仍可能触发 FRP 重试或中转，不能仅凭通道就绪确认保证每次五六秒完成。
