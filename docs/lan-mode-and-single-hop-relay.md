# 离线局域网模式与单跳中继需求讨论

讨论日期：2026-10-26。本文记录需求、已确认选择和工程评估，不表示局域网功能已经实现。本次交付仅为文档，不修改客户端、服务器或运行时打包行为。

## 1. 本轮讨论的两个问题

### 问题一：离线局域网模式如何发现、认证和连接设备

在没有互联网、无法访问公网中心的环境中，用户可以进入局域网模式，发现设备并在组内建立连接。同一个局域网允许多个相互隔离的组。需要明确免云账号入口、组身份、设备信任、会话占用，以及 SSH 与 FRP 的职责。

**已确认：局域网模式继续使用 FRP。** StarBridge 负责准入和会话生命周期，FRP 提供受控通道，OpenSSH 负责 SSH 协议、登录认证和业务数据加密。当前方向不另外编写一套替代 FRP 的 TCP 数据转发网关。

### 问题二：仅允许经过一个中继节点，是否值得增加这项能力

设 A 无法直接连接 C，但存在可以承担转发的 B，希望支持 A 经 B 连接 C。评估范围包括跨局域网设备信息同步、节点更新、路由失效和会话清理，不能只按双向复制 TCP 数据的原型工作量判断。

**尚未确认：单跳中继是否进入首版。** 用户允许在增量过大时放弃。本文建议先建立离线直连基础，再用最小三节点原型验证受限单跳；此建议不等于用户已经批准实现或上线中继。

| 项目 | 当前状态 |
| --- | --- |
| 完全离线，不依赖公网中心和云账号 | 需求方向已明确 |
| 自动发现、组内连接、同网多组 | 需求方向已明确 |
| 局域网继续使用 FRP | 用户已确认 |
| 组名只作显示，随机组 ID 与邀请码用于认证 | 建议方案，具体交互待定 |
| 每台客户端按需运行 frps，连接目标时使用目标的 frps | 建议部署方案，需实机验证 |
| 最多经过一个中继节点 | 候选能力的明确范围 |
| 首版包含自动单跳中继 | 待决策 |

## 2. 离线局域网的共同基础

### 2.1 入口与交互

- 登录页提供免云账号的局域网入口；主界面可提供模式切换，具体布局待定。
- 进入后创建或加入组，保存本地身份和组凭据；后续启动自动发现并认证同组成员。
- 自动发现、认证和更新列表，可以自动完成。SSH 业务会话按现有连接操作发起；无人值守自动连接属于另行定义的规则。
- 互联网模式与局域网模式使用明确的上下文，不伪造云登录态，也不因公网登录失败而自动放宽认证。

### 2.2 发现、组与设备身份

建议使用 mDNS/DNS-SD 发布和发现服务，例如 `_starbridge._tcp.local.`，并保留手动输入地址的引导方式。公告只提供公开的协议版本、组标识、设备标识和入口信息，不发布组密钥、FRP 凭据或私钥。

组名称是显示名称，随机组 ID 区分同名组。邀请码携带入组所需的随机秘密；“同组名即可加入”只能提供开放分组，不能提供成员认证。邀请码、首次配对和成员撤销的具体机制仍需确认。

每台设备应有本地持久的密码学身份，与云账号 token 解耦。发现记录只生成候选设备，经过认证后才可授权 SSH 公钥。目标 SSH 主机公钥也应通过可信流程绑定，不能直接信任广播或中继提供的地址。

多组隔离指列表、成员认证和访问授权隔离，不表示局域网观察者无法看到设备存在。第一版可先限制每个实例只有一个当前活动组。

## 3. 局域网继续使用 FRP

### 3.1 受控的实际含义

现有公网流程由 StarBridge 中心检查身份、能力和占用，通过后创建会话并分配 FRP 路由。客户端启动相应 frpc；会话结束时回收对应进程和通道。FRP 执行通道，业务占用规则属于 StarBridge。

SSH 直接开放到局域网后，SSH 的密钥认证仍有效，但它不会自动检查 StarBridge 的设备占用。因此保留受控的 FRP 通道有利于沿用会话管理。

占用限制针对设备会话和方向。同一获准通道内打开多个 SSH shell、SFTP 连接，不等于另一台设备申请了新会话。复用 FRP 不等于天然限制 SSH 连接条数。

### 3.2 离线 frps 的建议部署

沿用当前 STCP/XTCP 架构仍需要 frps；完全离线时必须在局域网内提供。建议每台客户端具备按需管理 frps 的能力，直连时将 frps 放在目标设备上，避免固定组主机和主机选举。

```text
A 连接 B，采用 STCP：

A 的 SSH → A 的本地 visitor/frpc → B 的 frps
                                      ↓
                                B 的本机 frpc → B 的回环 sshd
```

这条数据路径只有 A、B 两台机器。在产品层面属于“局域网直连”，FRP 协议类型仍是 STCP。首版无需为了这个路径使用 XTCP 打洞，也不使用公网 frps。

这是待验证的集成方案，不是当前客户端已有能力。现有端侧发布包只带 frpc；实施时需要增加 frps、许可证及校验清单，并管理监听端口、凭据、启动失败和退出清理。frps 管理接口保持本机可访问，不向局域网暴露管理凭据。

### 3.3 身份、授权与状态

- 组成员认证通过后才下发所需 FRP 凭据。frps 接入令牌与每条会话的访问密钥分别管理，不能把共享服务器令牌当作完整的会话授权。
- 每次获准会话绑定双方设备身份、唯一会话 ID、代理名和会话密钥。不能只改界面状态而让旧代理继续提供访问。
- 终止时关闭对应 visitor/proxy，清理连接、端口与占用；迟到消息不能重建已结束通道。
- SSH 继续校验目标主机公钥，保持业务数据加密；FRP 启动成功不等于 SSH 已就绪。
- 现有 `SessionPath::Direct/Relay` 与 XTCP/STCP 配置选择存在耦合。实施时需分开表达网络模式、是否经过第三台设备和 FRP 类型，不能把 LAN 的 STCP 误标为公网中转，也不能因显示“直连”而自动选择 XTCP。

## 4. 单跳中继的严格范围

“单跳”指至多经过一台中继电脑 B，路径为 A—B—C。连接建立后两方向的数据都经过 B，不是只转发一个方向。不支持 A—B—D—C 这样的链式中继。

```text
A 的本地 visitor/frpc → B 的 frps ← C 的 proxy/frpc → C 的回环 sshd
```

复用 STCP 时，必须验证 **A、C 都能主动连接到 B 的 frps**。抽象地说“A 能访问 B，B 能访问 C”不足以保证这个具体部署可行；防火墙可能不允许 C 反向连接 B。首版遇到这种拓扑应明确返回不可用，不自动扩展反向隧道或其他穿透方案。

B 可以是一台普通客户端设备，但必须能够与两侧建立所需控制连接，并允许提供中继。两边完全隔离、没有可达引导入口时，发现协议不能凭空建立通信。

为控制增量，候选首版限制为：

1. 只服务同组已认证设备，B 显式启用中继；不成为任意 IP/端口代理。
2. 优先直接连接；直连不可用时按确定顺序尝试有限个单跳候选。
3. B 只介绍自己的直接认证邻居，不转发别人介绍的间接路由。
4. 会话一旦建立就固定路径；故障时明确失败，用户重试重新选路。不中途无感迁移现有 SSH 会话。
5. 不做全网拓扑复制、Gossip、DHT、主机选举和按带宽动态选路。
6. 控制连接的建立不占用普通 SSH 业务角色；业务会话仍执行设备准入。

## 5. 信息同步和节点更新的最小方案

### 5.1 本地邻居与间接可达列表

每台设备维护自己的已认证直接邻居。B 通过与 A 的可信控制连接，提供“允许申请经本机访问的直接邻居”摘要。A 将其保存为一条 `目标 C，经 B 可申请连接` 的候选路径，不将 C 当成本地直接邻居。

摘要更新至少包括组 ID、目标设备 ID、资料版本、必要的设备资料和本次公告代次；B 的可用中继入口由认证连接绑定。端点 IP 只属于路径，不能代替稳定设备身份。同名设备不得合并，不同来源介绍的同一设备应合并展示、保留各自路径。

A 不能把 B 的转述当作 C 已通过认证或当前一定空闲。最终申请仍需按基础 LAN 信任协议验证 C 的身份、主机公钥和当前准入结果。若控制消息经过 B 转达，也要保留对原始发起设备的可验证身份。

### 5.2 更新、失效与恢复

- 首次认证和重连后发送完整快照；小组规模下可以先用周期快照刷新，增量事件只作为加速，不必首版实现复杂增量日志。
- 认证邻居增加、离开或资料变化时触发刷新；公告使用启动标识和序号，结合当前认证连接拒绝乱序、重复及旧连接的迟到更新。
- 候选路径使用本地单调时钟计算存活期限。控制连接断开时立即失效对应来源路径；未能及时检测的故障由心跳和过期兜底。
- C 掉线后 B 撤销对 C 的介绍；B 掉线后 A 删除所有经 B 的候选路径，保留其他来源路径。
- C 换 IP 时按设备 ID 更新路径；B 重启需重新认证和获取快照，不能把旧通道、旧凭据或旧会话复活。
- 列表区分“发现到”“可申请经 B 连接”“正在连接”“SSH 已就绪”；缓存中的在线、空闲状态仅供提示。

精确心跳、刷新和过期参数在原型中确定。首版不要求全组瞬时一致，要求实际建联重新校验、故障最终可清理。

### 5.3 三方会话与占用

业务会话始终表示 A→C，B 是中继服务提供者，不拆成 A→B 和 B→C 两条普通业务会话。

A 先原子预占本机发起角色，通过 B 转达给 C；C 原子检查和预占目标角色；B 接受中继资源预约，再为本次会话启动或分配相应 FRP 资源。任一步失败、超时或取消，都按同一会话 ID 幂等回滚各方资源。多条并发出站协商分别记账，不能因为其中一条失败而清除其他会话的占用。

设备准入最终由各设备本地状态裁决，不能由 B 的缓存替 C 决定。重复申请返回原会话；准备阶段具有有效期和代次，崩溃或断网后不保留永久占用。B 的转发容量单独记账并设上限；它是否可以同时参与普通 SSH 会话属于待确认策略。

B 退出或相关 frpc/frps 故障后，关联业务会话结束，A/C 释放相应占用并停止导出旧 SSH 命令。只影响经过该中继的会话。

## 6. 相比不支持中继，额外需要多少工作

### 6.1 估算前提

以下为设计阶段的粗略预算，不是实测代码差异或交付承诺。比较基线是已经完成的离线 LAN 直连版本，已经具备设备身份、组认证、直接邻居控制连接、局域网 frps 管理、会话准入、SSH 验证和进程清理。

这些共同基础目前尚未全部实现，不能把它们的开发成本计入单跳增量，也不能将整个离线模式误估为下面的规模。

| 额外部分 | 复用内容 | 产品代码粗估 |
| --- | --- | --- |
| 单跳路径模型、消息和校验 | 现有 serde、节点/会话模型 | 约 80–160 行 |
| 邻居摘要同步、合并、代次和失效 | 基础 LAN 控制连接、Tokio 定时任务 | 约 180–400 行 |
| 三方准备、FRP 路由选择、回滚与清理 | frpc 配置生成、进程监管、就绪验证 | 约 250–500 行 |
| 中继开关、路径和失败原因展示 | 现有客户端 UI 与事件状态 | 约 80–180 行 |

按上述边界，产品代码按约 **600–1300 行**预留；三节点测试与隔离网络脚本另约 **300–700 行**，合计约 **900–2000 行**。代码包含 Rust 和必要的 UI 代码，计数随模块拆分和测试复用方式变化，置信度较低；完成直连基础和三节点原型后应重新估算。这里不承诺工期或相对百分比。

判断是：**单跳属于中等且可控的增量，主要成本在跨网段候选信息和三方生命周期。** FRP 已承担数据转发，不需要重新实现传输协议。节点数量、网络策略和失效测试比正常路径的代码行数更影响交付风险。

如果只手动指定 B，可以省掉自动介绍和选路的一部分工作，但身份校验、三方准入与故障清理仍然必须存在。若要求任意网络方向都可中继、任意多跳或现有 SSH 无感换路，上述估算失效。

### 6.2 现成组件是否还能进一步省事

- **FRP**：继续承担 STCP 转发、连接承载和代理生命周期，复用项目已有组件；直接路径与经 B 路径主要区别是 frps 位于哪台设备。
- **mdns-sd**：负责本地链路发现；跨网段候选信息经已认证控制连接传播，不把 mDNS 广播直接跨网复制。
- **Tokio、Axum、Serde、Reqwest**：项目已有，可复用控制消息、连接管理、定时刷新和请求超时。基础控制连接的认证方式需在 LAN 设计中确定。
- **libp2p Circuit Relay v2**：可参考其预约、续期、断开失效与资源限额思路；本轮不因单跳能力额外引入另一套中继数据面。整体换成 libp2p 属于另一项架构选择。

现成组件能省掉大量底层实现，但不能代替本项目的分组、设备资料同步、角色占用和界面状态规则。

## 8. 原型与验收边界

### 8.1 先验证共同基础

完全断开互联网，运行两台设备：无需云登录、可组内发现和认证，经目标本机 frps 建立 STCP/SSH；验证目标占用、同向复用、终止与重启清理。确认客户端可可靠打包和启动 frps。

### 8.2 再验证单跳的决定性场景

| 场景 | 必须达到的结果 |
| --- | --- |
| A→C 被网络规则阻断，A/C 均可连接 B 的入口 | 通过 B 获得候选目标并建立真实 SSH，关闭 B 后数据立即或按超时失败 |
| 只满足 B→C，C 无法连接 B 的 frps | 明确说明此路径不满足当前 STCP 前提，不能假报成功 |
| C 改名、换 IP、退出、重启 | 同一设备身份更新；路径过期与重新认证正确；不复活旧会话 |
| B 退出、重启或禁用中继 | 对应路径和会话失效；其他直接会话不受影响 |
| 双中继介绍同一个 C、乱序快照与迟到通知 | 一个设备条目、多个来源路径；撤销一个来源不删除另一个；旧通知不复活路径 |
| A→C 与 D→C 同时申请，或协商中取消 | 目标仅接受一个有效会话；各方最终释放失败预约，不因部分成功残留占用 |
| B 伪报目标、跨组申请、旧凭据重放 | 按组和设备认证拒绝，不依据 B 的缓存授予访问 |
| 直连恢复、已建立中继会话仍在运行 | 当前会话保持原路径；后续新会话优先直连，不自动迁移旧 SSH |
| 试图传播或建立第二级中继 | 拒绝，不出现链式路径或转发环路 |

同一台电脑上跑三个 localhost 实例只能验证进程与协议，不能证明跨局域网发现、路由和防火墙条件已通过。至少需要隔离子网/网络命名空间或真实多网段设备验证，并覆盖 Windows/macOS 的端口权限与休眠恢复。

## 9. 建议的实施顺序与尚待确认事项

1. 先实现和验证免云账号 LAN FRP 直连，建立独立于公网中心的组、身份和会话生命周期。
2. 数据模型预留中继节点与路径来源，先不实现全网路由。
3. 单独制作受限的三节点原型，验证 FRP 端点替换、节点失效和并发回滚，再更新增量评估。
4. 若符合上述网络前提且生命周期可靠，单跳值得作为可选阶段实现；若需要反向穿透、链式中继或全局拓扑，首版暂缓。

仍需确认：组邀请码与成员撤销方式、局域网入口布局、中继是否纳入首版、中继默认开关、B 与普通业务会话能否并存及容量限额。上述事项不影响“局域网继续使用 FRP”这个已确认选择。

与既有文档的关系：[未来路线](future-roadmap.md)中的离线方向继续保留；LAN FRP 的具体部署建议以本文讨论为补充。实施时应同步更新运行时打包文档中“端侧不带 frps”等旧约束。本次不修改这些历史文档，避免把待验证方案写成已实现架构。
