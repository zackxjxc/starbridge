# 局域网与虚拟机能力分阶段路线

本文用于确认近期实施边界，详细技术分析分别见 [局域网需求讨论](lan-mode-and-single-hop-relay.md) 和 [虚拟机通道与多模式规划](vm-channel-and-mode-planning.md)。

## 第一步：局域网模式，不做跳板

目标是在没有外网和云账号的局域网中，让同组设备自动发现并建立受控连接。

- 通过组名、随机组 ID、邀请码或首次配对建立组上下文；组名本身不作为信任凭据。
- 通过 mDNS/DNS-SD 或手动地址发现候选设备，认证后才加入设备列表。
- 局域网数据通道继续使用 FRP，StarBridge 负责组认证、设备身份、会话占用、FRP 凭据和清理，SSH 负责业务连接和主机密钥校验。
- 首版只支持 A 与 B 两端的局域网直连。
- 不支持 A 经 B 连接 C，不做自动跳板、跨网段路由、多跳拓扑或第三节点中继。

第一步的完成条件是：两台断网设备可以发现、认证、建联、真实 SSH 验证和清理；跨组设备被拒绝；目标重启、IP 变化或 FRP 进程退出后不会遗留可用旧通道或永久占用。

## 第二步：虚拟机模式，先做宿主机到 guest

目标是在虚拟机没有可用网卡或无法获得 IP 的情况下，由一台宿主机控制多台虚拟机。

- 先选择一个明确的 hypervisor、宿主 OS 和 guest OS 组合，验证 vsock、VMCI、Hyper-V Socket 或等价专用通道。
- 先实现 H→VM1、H→VM2、H→VM3 的固定星形拓扑，维护 guest 身份、通道状态、心跳、重启和快照/克隆冲突。
- 虚拟机通道绕过普通网卡，但仍依赖对应虚拟设备、内核/集成服务和权限；缺少这些支持时需要明确提示或离线安装。
- 是否让 VM1 通过宿主机控制 VM2，放在宿主机到 guest 稳定后再评估。它可以复用固定宿主机的会话协调和受控转发，但需要单独决定占用规则、并发、权限和故障回收。
- 不因为未来可能支持 VM 间通信，就提前把局域网单跳做成通用多跳路由系统。

## 两步之间的关系

两步共享节点身份、会话生命周期、占用规则和模式说明，但传输实现不同：局域网阶段以 mDNS、组认证和 LAN FRP 为主；虚拟机阶段以固定宿主机目录、平台通道 provider 和 guest agent 为主。完成第一步不是第二步的技术前置，完成第二步的宿主机到 guest 也不自动承诺 VM 间互控。

多模式 UI 需要预留普通模式、局域网模式、虚拟机模式和模式说明等多个 item。模式选择、账号/组/宿主机上下文和实际会话路径要分别表达；UI 设计在上述两个阶段的支持边界稳定后再实施。
